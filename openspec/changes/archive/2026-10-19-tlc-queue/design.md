## Context

Projects that use TLA+ keep their models in small directories (100–400 KB each: `.tla` modules and `.cfg` configurations, up to about 90 configurations per directory) and check them before committing. Small configurations finish in seconds; large ones run for hours with tens of gigabytes of fingerprints. Today a script (`tla/tlc.sh`) runs them on the laptop with a time cap and an opt-in probe (`tla/probe.sh`, calibrated at 15 minutes) that stops searches still widening, so several never finished. A home server, `pve` (32 cores, 125 GB, rootless podman reached through the `pve` docker context), will run TLC in containers. Below, "the VM" means that side: the runner container there and the job containers it starts (D9, D10). Agents (Claude sessions in several worktrees and projects, all on one laptop) submit work and need to follow it: where it runs, how far it is, when it should end, and its result.

The specs state the behaviour; this document gives the mechanism and the reasons.

## Goals / Non-Goals

**Goals:**
- One command for agents; tlcq decides where each job runs.
- Run each job on the VM as fast as the VM allows, from any project or worktree, with no per-project setup on the VM; limit only its time, so no job holds the VM forever.
- Never hold the laptop's CPU for a run longer than 5 minutes, unless an agent forces it with `--local`.
- Identify a result by exactly the model text it checked, committed or not.
- Give agents enough progress data to decide whether to keep a run going.

**Non-Goals:**
- A pre-commit gate (a later change; the cache it needs is in this one).
- TLC's distributed mode (TLCServer and workers on several machines).
- Several VMs, or several laptops sharing one VM.

## Decisions

### D1. The interface
```
tlcq submit <dir> [cfg…] [flags] [--config <file>|-]   verify, place, reply with a report per job
tlcq status [id…]                  report this agent's jobs (or the named ones); the agent polls it
tlcq ls | cancel <id> | fetch <id>
```
The agent submits, gets a report (id, machine, running or its queue position, cached, attached, refused), and polls `status` as often as it likes; the job-status spec lists the report's fields. `status` with no ids covers the agent's current jobs, read from its follows (D6): per key, the latest, plus any older one whose run is still queued or running with its key's entry, so one call shows them all. Nothing blocks and nothing waits for a notification; decisions that fall due while nobody polls (D9) are made by the job's supervisor and reported at the next poll.

Flags of `submit`: `--all` (include max configurations when none is named), `--fast`/`--slow`/`--max` (D5), `--replace` (D6), `--timeout <duration>` (D9), `--local` (every job on the laptop, uncapped), `--vm-on-timeout` (D7), `--must-fail-only` (D8), `--tlc-opt=<option>` (D3), `--config <file>` or `--config -` (stdin) for a submission config (D4).

Exit codes. `status` exits 0 unless a job it reports failed: 3 when any ended `timeout`, `cancelled` (one still stopping included), `error` or `never sent` (D6), else 1 when any is `unexpected`; queued and running jobs exit 0. `submit` exits 0 once every job is placed, cached or attached; 3 when its commit outcome is unknown or its preflight connects and then fails (D6). A refusal, a usage error or an `invalid` commit (D6) exits 2. `fetch` exits 0 when done, 2 for an id neither machine knows or a VM job while the VM is unreachable, and 3 when its VM call connected and then failed; `ls` exits 0, reporting VM jobs with their last known state while the VM is unreachable, and 3 when its VM call connected and then failed. Refusals are all-or-nothing: a command decides every one before it sends, runs, supersedes or cancels anything, so a refused command does none of these.

### D2. A job is the modules and one configuration, sent on stdin
A job holds every `*.tla` in the model directory and in its EXTENDS directories (the config's `extends`, D4), except TLC's trace files, plus the one configuration it checks; the tarball's layout is `model/` (the configuration as `model/job.cfg`) and `lib/0/`, `lib/1/`…. Beside it travels `job.json`: the spec module, the options, the expectation and its source, the flags, and the submitter entries (D6).

Both machines run a job the same way: the supervisor (D7, D10) extracts the tarball into the attempt's own directory (D10; on the laptop, the run's subdirectory, D7) and runs TLC there, every path absolute: `<dir>/model/<Spec>.tla`, `-config <dir>/model/job.cfg`, `-DTLA-Library=<dir>/lib/0:…`, `-noGenerateSpecTE`, `-metadir <dir>/scratch`, the slot's resource settings (D9), the allowlisted options. Nothing runs in the worktree, so edits during a run change nothing and TLC writes no file there.

The client sends jobs in one `tlcq commit` call to the runner (D6, D9), writing each `job.json` and tarball to stdin. The command line carries only fixed verbs and ids matching `^[a-z0-9-]+$`, so it is safe whatever the transport. The VM validates every tarball and recomputes every id before applying anything (D6).
- Alternative: a git commit pushed to the VM. Rejected: models are checked before they are committed, and a model directory is small enough to copy.
- Alternative: the whole model directory. Rejected: an edit to any configuration would change every sibling's id, and stray files (a `states/` directory, logs) would travel too.

### D3. A content-hash id
A job's id is the SHA-256 of a manifest: the spec module name; the sorted tarball paths, each with the SHA-256 of its bytes; the options; and the jar version. The configuration's name is not in it, so renaming a configuration keeps its results.

The option allowlist starts with `-deadlock` alone. An option joins it deliberately, and only if its result is deterministic and the run ends on its own, so never `-simulate`, `-seed`, `-depth` or `-continue`. Resource settings (workers, heap, off-heap memory, `-lncheck final`) and time caps change only the speed or when a run is cut, so they are not in the id.

The jar version is the SHA-256 of `tla2tools.jar` and `CommunityModules-deps.jar`. Each machine hashes its own jars, and the VM refuses a mismatch, so a stale laptop never mixes results across versions.

### D4. The submission config
A submission is described in TOML, one schema wherever it comes from. An example from a real project (`juliet`, whose spec EXTENDS `november`):
```toml
spec = "Juliet"
extends = ["../november"]   # other directories whose modules the spec reuses
replace = true
cfgs = [
  "JA.cfg",
  { name = "JA_10.cfg", must_fail_only = true },
  { name = "JA_08_max.cfg", timeout = "24h" },
]
```
Fields: `spec` (the spec module, required from some source), `extends` (directories relative to the model directory, so `../november` is allowed; the tarball remaps them as `lib/<n>/`, D2), `cfgs` (each a name, or a table with `name` and its own `expect`, `timeout`, `must_fail_only`, `tlc_opts`), and the flags of D1 as keys (`all`, `replace`, `local`, `vm_on_timeout`, and `expect`, `timeout`, `must_fail_only`, `tlc_opts` as defaults for every configuration). Unknown keys are refused.

It comes in layers, each overriding the one before key by key: `<dir>/tlcq.toml`, if there is one (the directory's defaults, typically `spec` and `extends`, so a plain `tlcq submit <dir>` works); then `--config <file>`, or `--config -` reading the same TOML from stdin; then the command line, whose configuration names replace `cfgs` and whose flags set those keys. A configuration's own fields override the defaults. With no `spec` from any layer, the command exits 2 and says so.

### D5. Expected duration
Each job is expected short (under 5 minutes), long, max (over 1 hour), or unknown: by a flag, else by a configuration name suffix (`_fast`, `_slow`, `_max`), else by the laptop's history, first match wins:

| Lookup | Key | Use |
|---|---|---|
| exact | spec hash + configuration hash + options hash | the key's expectation |
| configuration | spec module name + configuration hash + options hash | the key's expectation, shown as "from an earlier spec" |
| name | spec module name + configuration name | the key's expectation, used only when it is long or max |
| none | | unknown |

The spec hash covers the manifest without `model/job.cfg`. A record holds the implied expectation, the duration, the outcome, the place and pointers to the run's progress curves, one per attempt (D15), one per job id and end. A finished run records its duration; a run that ended early records a lower bound (long at or past 5 minutes, max at or past 1 hour, nothing below). A key's expectation is its last finished record raised by any later lower bound, never lowered by one: a short cancel after a 3-hour run must not send the next run into a 2-hour cap. A run superseded after an hour records max, and a spec-only edit inherits that through the configuration key, as intended.

Why the fallbacks: the exact key alone would forget everything on each spec edit. The configuration key keeps the hint across spec edits; the name key catches an edited constant, and may only lengthen, since a stale "long" costs one VM run while a stale "short" would cost a cap. Durations are in awake time and compared as they are, wherever they ran. A suffix outranks the history, so a `_fast` configuration that takes 10 minutes times out every time; tlcq warns, and renames nothing.

### D6. Preflight, commit, records
The laptop keeps a record per job it placed, `<state>/jobs/<id>/` (D13): its state, tarball, entries, a generation counter that every write to the state or entries bumps, and, for a laptop job, a lock that its supervisor holds while it lives.

```
laptop ──▶ ended               (a laptop job)
   └──▶ moving ──▶ vm ──▶ ended
vm ──▶ ended                    (a job sent to the VM)
sent? ──▶ vm ──▶ ended          (a commit whose outcome is unknown)
   └──▶ never sent
```

**Locks.** All laptop locks are `flock`s, freed when their process dies. One placement lock serialises placement, supersede, cancel and moves, across every worktree, so no command sees another's work half-done: a command holds it from its preflight to its last record write and releases it before it returns; `status` and `cancel` read their snapshot (records, counters, job locks, follows) under it, make their VM call unlocked, then apply their record changes under it, each only if the record's generation counter is unchanged since the call (else they poll again); a supervisor takes it to move a job (D7) and to write its end state, in this order: take the placement lock, write the state (bumping the counter), free the job lock, free the placement lock. A command only tries a job lock, never blocks on one, so it cannot deadlock with a supervisor; the one exception is `cancel` after it has SIGKILLed the supervisor (D7), which cannot then be waiting on anything. The placing command closes its own copy of a job lock's descriptor once the supervisor has started, and TLC never inherits it. Cache files are created exclusively, so the first result for an id wins; history appends check (id, end) under the history lock, so each run is recorded once. On the VM, every verb reads and validates its payload first, under its own deadline, and only then takes the admission lock (D9) to apply it, so a stalled connection never holds the lock, and once it holds the lock the apply runs to completion, whatever the deadline: it ignores SIGHUP and SIGPIPE, builds its reply after the apply, releases the lock, then writes the reply under its deadline, ignoring a failed write (`fetch` lists its files under the lock and streams them after); it stops containers without waiting for them, so the stop hook, which needs the lock, never waits on the verb holding it. Every verb's payload travels on stdin. Each VM call has a connect timeout and an overall deadline (D13). The VM is unreachable when the preflight (or a poll) cannot connect. A preflight that connects and then fails exits 3 with nothing written; a poll that fails is retried; any other call that fails has an unknown outcome.

**Tokens.** Every commit, a move's included, carries a random token, kept in the laptop's `sent?` or `moving` record and in its follows. On applying a commit, the VM records its token on the run each job reached, a `cached` answer's result included; an `invalid` commit records it as not applied. A lookup answers for each job of the commit, by id (a job the commit did not store, a refused `now-or-refuse` one, is not applied). A lookup (a preflight's or a poll's, under the admission lock) of a token the VM has not applied records a tombstone for it, and a commit whose token is tombstoned aborts under the lock, applying nothing. So every answer is final, reached or not applied, whatever the clocks and however late a dropped connection's commit arrives; the tombstone is the only thing a preflight writes. A poll sees only tokens of commands that have finished or died, since `status` and `cancel` read their snapshot under the placement lock, which a placing command holds through its commit.

**Follows.** Entries say who holds a job; what an agent's reports follow is kept apart, in a follow per entry an agent places (one per configuration name of a merged job), `<state>/follows/` (D13): its label, key, id, a placement number fixed when it is created, and what it follows: a run name, a cache hit's result, or a commit's token. Its writers, all under the placement lock:
- the command that places it: the write-ahead step, with the commit's token, for a job it sends; a cache hit's, with its result, once every refusal is decided and before the commit; the records step otherwise (a laptop run, a laptop attach, an offline attach naming its pending entry's run), the unknown-outcome path included. A placement whose id, run and key match a follow the agent already has writes none;
- the records step, for a sent job, rewriting the token to what the VM answered: the run started, queued or attached to, the cached result, or for a refused `now-or-refuse` job its laptop run; an `invalid` answer removes it instead;
- a preflight or poll, which sends the tokens of follows still holding one and rewrites each to what it reached, or, once the token is not applied (Tokens), to `never sent` (even while the id runs for another worktree).

Nothing else changes a follow, neither a mirror refresh nor the id being placed anew, so a record keeps following the id (the laptop must not run a job the VM holds; refreshing a record by its token instead lets a lost attach run the job on the laptop beside the VM's run, `PL_sentbytoken`) while each agent's report follows its own run. `status` with no ids finds the agent's follows by worktree path and `$TLCQ_AGENT` (unset matching unset; never by branch) and reports, per key, the one with the highest placement number, plus any older one whose run is still queued or running with its key's entry (one still holding a token while the VM is unreachable counts as running, reported unreachable). An older follow drops out once its run has ended or been cancelled (its container still stopping included) or a supersede has removed its key's entry from it, so replacing one's own version, shared or not, neither keeps it in the report nor makes `status` fail.

**Entries.** A job keeps one entry per submitter: worktree path, model directory within it, spec module, configuration name, label. A `vm` job's entries live on the VM; the laptop keeps a read-only mirror, refreshed by every preflight and poll, and uses it only while the VM is unreachable. An attach made while the VM is unreachable is stored, once every refusal is decided, as a pending entry in the job's record, naming the run it attaches to: the record's run name, or for a `sent?` record its commit's token (below), which the refresh resolves to the run that commit reached. The next commit flushes every pending entry first (entries only, no tarball), each onto its own run only; its records step clears them, bumping the counter; an unknown or invalid commit keeps them. A pending entry whose run has ended, or that the VM does not know, is dropped, and the attacher's `status` reads the outcome. A `--vm-on-timeout` move carries every entry. An older version of a new job is a queued or running job with an entry (pending entries included) matching the new job's worktree, model directory, spec module and configuration name, and another id.

**Input checks.** First, without the lock, the command checks its input (the submission config, D4; the allowlist; duration flag, a `--must-fail-only` property the configuration does not list, and the VM's tarball checks: names, file types, size and entry limits, so the only `invalid` left is a jar change between the preflight and the commit) and computes the ids, merging a command's jobs that share an id into one job with one entry per configuration name, placed once (its expectation the longest of its names' (short < unknown < long < max), skipped as max only if every name is, its history record and report listing every name); any failure exits 2 with nothing written. With no configurations named and no `--all`, jobs expected max by their suffix (a merged job only if every name is) are set aside for the skip-max listing (job-submit spec, One command) now.

**Preflight.** Under the placement lock, one VM call, read-only but for token tombstones (Tokens), sends the ids, jar version, keys, and every id the laptop holds in `vm`, `sent?` (with its token) or lock-free `moving`, and the tokens of follows still holding one; it returns the jar check, the run each token reached, if any, each id's state (cached with its result, queued, running, stopping (cancelled, its container not yet gone), or ended with outcome, duration and any lane decision with its probe numbers) and entries, and the older versions on the VM. The laptop then refreshes its records (the same refresh `status` applies):
- queued or running on the VM: `vm`;
- cancelled on the VM, its container still stopping: stays `vm`, but cannot be attached to; a new submit of it queues a new run, in its own container (D10);
- cached or ended on the VM: the result or outcome recorded, the record ended;
- `sent?` unknown to the VM, once its token is not applied (Tokens): `never sent`, an outcome of its own (uncached, no history record);
- lock-free `moving` unknown to the VM, once its move's token is not applied: `timeout`, as its laptop run ended;
- `vm` unknown to the VM: `error`;
- lock-free `laptop`: an orphan (D7);
- while the VM is unreachable, `vm`, `sent?` and lock-free `moving` stay as they are: the VM may hold them.

Then it updates its mirror and history and computes each job's expectation (D5); with no configurations named and no `--all`, jobs every name of which is max, by suffix or history, are set aside for the skip-max listing too, and take no further part. Each remaining job is: a cache hit (the laptop's cache, or the VM's, copied); an attach, to the VM if the preflight reports it queued or running there (with or without a laptop record, which is then written as `vm`), to the laptop if its laptop job's lock is held, or to a `vm`, `sent?` or `moving` record while the VM is unreachable; or new. Every refusal is decided now:
- a long or max job while the VM is unreachable, unless `--local`;
- an older version running while the new job is no cache hit (an attach counts as a run: it adds this worktree to a running job), unless `--replace`, which is itself refused while the VM is unreachable and the older version is on it; while unreachable, a `vm`, `sent?` or `moving` older version counts as running;
- a jar mismatch.

**Routes.** Before the commit, the client hands out the laptop's free slots (the slot count minus the laptop jobs running or waiting) once, in submit order: unknown jobs first, then short ones. Long and max jobs are queued on the VM; an unknown job with a slot runs on the laptop, without one it is queued on the VM; a short job is sent `now-or-refuse` if it holds a slot, else `now-or-queue`. A cache hit or an attach wins over `--local`, which routes every other job to the laptop.

**Commit.** One VM call, one stdin stream, with an overall deadline. The VM first validates every tarball and recomputes every id; any failure aborts the whole commit with nothing applied, answers `invalid` for that job, and the command exits 2, as for a refusal. Otherwise, after settling (D10), it applies, in order: pending entries (one whose run has ended or is unknown is ignored and answered `ended`, and the records step clears it), the jobs, supersedes, then one admission round. Every job bound for the VM, attaches to the VM included, travels with its tarball and is applied idempotently by id: live, it is attached; cached, the result is returned; ended uncached, cancelled but still stopping, or unknown, it is queued anew (a new run, D10). Jobs come before supersedes, so a job that a new entry has just attached to survives the supersede. To supersede a job is to remove every entry matching the new job's key; a job left with no entry is cancelled, "replaced by <new id>" (also if it started since the preflight). The admission round follows the slot rules (D9), so a `now-or-refuse` job starts only if no older job takes the slot it could use. The VM answers per job: started, queued, attached, cached (with the result), or refused (a `now-or-refuse` job it could not start, a failed container start included; it is not stored, and takes its laptop slot).

**Before the commit.** Once every refusal is decided, and before the commit, the command drops its worktree's pending entries on every older version it supersedes (so a commit whose reply is lost cannot flush them again later), and supersedes its laptop older versions (when it also attaches to one, the attach's entry goes in the same record write, so no cut-off command or `invalid` answer leaves it with no entry): those left with no entry are cancelled by `cancel`'s procedure (D7), under the placement lock it already holds, with a marker carrying the canceller's label and the new id. It also writes `sent?` for every job it is about to send (write-ahead), with its own entry in the job's mirror and the commit's token (random, sent in the commit; the VM keeps it on the run the job reached), so that while the VM is unreachable a later command from the same worktree recognises the job as an older version. Both orders are forced: if the command is killed after the commit, a job the VM took always has a laptop record, so a later command offline does not run it again; and no lost reply or killed command can leave an older laptop run beside the new one. The cost: if the commit then fails, the older laptop run is gone and the new one not placed, and the command exits 3 for the agent to rerun.

**Records.** After the commit, the command turns its `sent?` records into `vm` for jobs answered started, queued or attached, and ends those answered cached with the result (cache and history written); for a laptop job, it takes the job lock and writes the ticket first, then the `laptop` record, then starts the supervisor with the locked descriptor, so the lock is never free in between; and it adds each attach's entry on a laptop job's record (laptop attaches never go in the commit). If the commit's outcome is unknown, the `sent?` records and their token follows stay, the command writes the entries and follows of its laptop attaches, starts nothing on the laptop, reports it and exits 3; the next preflight, `status` refreshes them. If the VM answers `invalid`, nothing was applied: the command removes the `sent?` records it created (with their mirror entries), restores any it rewrote (state, token and mirror entries) to before the commit, removes the follows its write-ahead wrote (a cache hit's ended record and follow stay: its result is real), writes no entry of its laptop attaches, starts nothing, reports the laptop supersedes already done, and exits 2. With the VM unreachable there is no commit: short and unknown jobs go to the laptop, attaches store pending entries. A cache hit writes an ended record carrying the agent's entry, and its follow, once every refusal is decided, so that `status` shows it.

The protocol of this section and D7 is model-checked: `tla/placement/Placement.tla` (D14).

The laptop keeps the first result it holds for an id. An attached job keeps the first submitter's flags, with a warning when they differ. A cache hit is returned at the preflight, never committed, and supersedes nothing.

### D7. Runs on the laptop
One slot (configurable), 8 workers, 8 GB heap. Every laptop job, waiting or running, has a detached supervisor (`tlcq supervise <id> <run>`, its own process group; the VM's `tlcq exec` is an attempt's) that holds its job lock and its ticket (the lock handed to it as its stdin by the command that launched it, so it is never free between the two), so the job outlives the `submit` that placed it. Supervisors take the slot in submit order by ticket files, skipping (and counting as free) any ticket whose job lock is free; they start TLC only above a free-disk floor. TLC's scratch is deleted when TLC ends. Each run's markers, `result.json`, scratch and elapsed awake time (which the supervisor rewrites every minute) live in its own run subdirectory, so a job queued anew under the same id starts clean.

A run that passes 5 minutes of awake time is stopped, and the supervisor writes a timed-out marker. Then it either records the timeout and ends the job `timeout`, or, with `--vm-on-timeout`, takes the placement lock, sets `moving`, reads the entries, commits the job (same id, expected long, every entry, the laptop attempt's awake time, a token kept in the `moving` record) to the VM queue, sets `vm` and releases the lock, so no other command sees it mid-move; its agents' polls follow it. If that commit's outcome is unknown, or the supervisor dies mid-move, the job is left lock-free in `moving` and refreshed as in D6: on the VM it becomes `vm`, unknown to it it ends `timeout`. If the VM answers `invalid` (its jars changed meanwhile), the job ends `error`, and the report says why. `--local` runs have no cap unless `--timeout` sets one.

`cancel` takes the placement lock, writes a marker (carrying the canceller's label, and for a supersede the new id), and tries the job lock: if it gets it, the job is already an orphan, and nothing is killed. Otherwise it kills the supervisor's process group (SIGKILL, so the supervisor never waits on the lock `cancel` holds) and waits for the job lock to free. Either way it then applies the orphan rule itself before releasing the placement lock; this ends a waiting job and a running one alike, before `cancel` returns. A job on the VM, or an id the laptop does not know, is cancelled through the VM (D10). A job whose place is uncertain (`sent?`, lock-free `moving`, or any VM job while the VM is unreachable, which a `cancel` that cannot connect also means) cannot be cancelled: `cancel` exits 2 and says so. An ended job is left as it is and reported, exit 0. `cancel` exits 0 when done, 2 when refused or the id is unknown to both machines, and 3 when its VM call connected and then failed. A job in `laptop`, waiting or running, with its lock free is an orphan: whoever finds it records `cancelled` if a cancel marker is there (with the marker's label and any "replaced by" id, in `result.json`), `timeout` if a timed-out marker is, else `error` (the laptop restarted); appends the run's lower bound from its elapsed awake time (D5, once per id and end); and deletes its scratch and ticket.

### D8. The verdict
TLC's exit status sorts a run: 0 and 10–14 (the violations; an unwitnessed `_POSSIBLE` exits 10) go to the verdict; 75–77 and 150–151 (evaluation, parse and configuration errors) are deterministic, so `unexpected` and cached; anything else (255 covers an out-of-memory error and most failures), a signal or no exit is `error`. The verdict reads the configuration's leading `\*` lines for `must fail <Property>` (case-insensitive, first match) and matches TLC's `Error:` lines (`violated`, `never witnessed`, `Deadlock reached`), as `tla/tlc.sh` does. TLC checks `_POSSIBLE` predicates itself.

TLC stops at the first violation, so a variant breaking several properties may report any of them; the mismatch suggests `--must-fail-only`. `-continue` does not serve: measured on the pinned jar, it reports only the first invariant each state violates, in configuration order. So the flag rewrites the configuration on the client before hashing: the leading `\*` block kept verbatim; entry lists parsed keyword to keyword (`INVARIANT(S)`, `PROPERTY`/`PROPERTIES`, `_POSSIBLE`; several names per line, lists over lines, `\*` and `(* *)` comments); every entry but the named one dropped (all for deadlock; an emptied keyword may stay); exactly one `CHECK_DEADLOCK` line, `TRUE` for deadlock, else `FALSE`, since TLC rejects a second one (180 of the 244 `must fail` configurations in a real project already have one). A fixture covers each form.

`result.json` holds the outcome (with the canceller's label and any "replaced by" id, or the reason for an `error` such as too big), TLC's exit status and error lines, whether it ran out of memory, the states and depth, the place, slot and times, the lane decisions with their probe numbers, the attempt, and the log paths.

### D9. The VM: two slots, time caps, no resource caps
The VM exists to run TLC as fast as it can, so a job's resources are limited only by what else runs, and its time by its lane. The whole is the VM's cores and memory minus a reserve (default 1 core, 4 GB):

The VM has a 70% slot and a 30% side slot. Admission is first in, first out: the queue holds runs in the order of their first commit to the VM (a run requeued by an undo or a failed start keeps its place), unless a human has moved one in the UI (D16), and "oldest" below means first in that order. On an idle VM, the oldest waiting job takes both slots (100%), so it finishes as fast as it can; a max job takes the 70% slot alone only while a non-max job waits that the side slot could run next to it, since a max job holds its share for hours. While either slot is busy, the other one admits on its own: the 70% slot takes the oldest waiting job; the side slot the oldest waiting non-max job. A job keeps its share until it ends or is restarted, and a stopping attempt's share frees only when the attempt is settled (D10); a slot held for a restart takes no other job, and the restart takes 100% when the side slot is free too and no non-max job waits for it, else 70%. A max job resizes the same way as the side slot's use changes: at 70% with the side slot free and no non-max job waiting, or at 100% with one waiting, its supervisor restarts it just after TLC's next checkpoint (every 30 minutes), keeping that checkpoint for the restart to recover (D10), so a resize loses at most a few seconds of work.

```
idle                   → the oldest job at 100%; a max one at 70% if a non-max job waits
a job at 100%          → everything else waits (a short job goes to a free laptop slot, else queues)
70% busy, side free    → the side slot takes the oldest non-max job
side busy, 70% free    → the 70% slot takes the oldest job
both busy              → everything else waits (a short job goes to a free laptop slot, else queues)
```

A slot's share sets the container's `--cpus` and `-workers`, and caps its memory: an attempt's `--memory` is its share of the memory, but no more than what the VM has free when it starts (`MemAvailable`) less the reserve and less the room the running attempts may still grow into (each one's cap less its use), since pve shares its memory with things tlcq does not control, such as a VM that pins 32 GiB while it runs; so the caps never sum past what the machine has, and a job that outgrows its cap is killed alone instead of a host-wide OOM kill taking the largest job. Below 4 GiB it waits (it reports waiting for memory), as no attempt is made. The cap is the attempt's memory, split between heap and off-heap fingerprints (default 40% heap) as `tla/tlc.sh` does: `-Xmx… -XX:MaxDirectMemorySize=… -Dtlc2.tool.fp.FPSet.impl=tlc2.tool.fp.OffHeapDiskFPSet -fpmem 1.0`; max jobs add `-lncheck final`. A job starts only above a free-disk floor, since TLC's scratch reaches tens of GB.

**Lanes move up one step at a time, decided by the supervisor.** A VM job's supervisor (`tlcq exec`) watches TLC's progress lines and makes each lane decision itself, when it falls due, whether or not anyone polls; it records the decision and the probe's numbers in `result.json`, which `status` replies and the preflight's per-id state carry to the laptop, which records it in the history (D5).
The lane timers (the 15-minute decisions below) count on the VM, from the run's first VM attempt's start, so a moved run's laptop minutes and its queue wait do not count; caps count as given under Caps.
- Short: still running at 15 minutes, it becomes slow, whatever its probe says (a short job never jumps to max): its cap becomes slow's, and history records long.
- Slow (and unknown): 15 minutes after the job entered the slow lane (at its first VM attempt's start, or at its promotion from short), the size probe judges it: `ok`, it stays slow; `big`, it is max. What happens then depends on its slot:
  - at 100% (alone): if a non-max job waits that the side slot could run, restarted at 70% as max; else it becomes max in place, as in the 70% slot, keeping 100% (a restart throws its progress away, worth it only to run that job). Under the admission lock, and only if no cancel marker is there, the supervisor writes a restart marker in its attempt's directory, one write that also holds the 70% slot for the run (no other job takes a held slot), then stops TLC. The stop hook, finding the restart marker first by its order (D10), queues the next attempt at the head in the held slot, then records the end "restarted" with no outcome (D10's order), and its admission starts it (its own container, D10). The restart continues the same run for its agents, as a move does: same run name, every entry kept; the ETA starts a new curve segment.
  - in the 70% slot: it already has max's share, so it simply becomes max in place: it keeps its TLC options (no `-lncheck final`), and the supervisor extends its cap to max's.
  - in the side slot: restarted at 70% the same way if the 70% slot is free; else the supervisor writes a too-big marker under the admission lock and stops TLC, and the run ends `error` (too big).

  The decision travels in `result.json` and in `status` replies; the laptop records max for the job whatever its duration (D5).
- Max: the probe is shown, never acted on.

The probe is `tla/probe.sh`'s: it reads the progress lines 5 minutes before and at the probe time; `big` when queue / distinct ≥ 0.4 or the queue grew by ≥ 0.1 of distinct states over those 5 minutes. Those thresholds were calibrated on a real project's configurations at 15 minutes for "finishes within hours or not", the slow-or-max question; the probe time and thresholds are configurable per lane, and the probe's numbers go into `result.json` and the history for later tuning. A job in the 30% side slot explores more slowly, so its growth reads lower: a known calibration risk until there is data.

Caps: 2 hours slow or unknown (3 in the side slot, which is slower); 12 hours max; short has none of its own, since at 15 minutes it becomes slow: its slow cap counts from the attempt's start (the supervisor enforces caps, D10). An attempt that recovers a checkpoint (D10) carries on the earlier attempts' search, so its lane cap counts the run's VM time instead; a restart that starts afresh gets the whole cap. `--timeout` replaces every lane cap for its job and survives lane changes, counted over the run's VM attempts' running times (on the laptop it applies only with `--local`; the laptop's 5-minute cap is fixed).

**The runner.** One long-lived runner container on pve, `tlcq-runner` (`tlcq runner`, a compose service whose `restart: always` restarts it if it dies, and which the podman user's podman-restart service starts at boot), holds the queue on a state volume, takes the VM verbs, which the laptop runs inside it with `docker --context pve exec -i tlcq-runner tlcq vm <verb>` (under `vm`, apart from the agents' commands of the same names), and starts each attempt as a sibling container through the podman socket mounted into it (D10). A slot frees only when an attempt is settled or a held restart is dropped, so admission (under the admission lock) runs in `commit`, when the runner sees an attempt's container exit (the stop hook, D10), at the end of `cancel`, on each `status` poll, after a UI action (D16), every minute (which also catches freed disk), and at the runner's start; a `now-or-refuse` answer and the start it promises are one step. Admission starts nothing while the runner is stopping (it got SIGTERM, for a shutdown or a restart: it leaves a `stopping` mark on the state volume, which admission in every process reads and its next start clears, then exits), and a failed container start leaves the job queued in its place (a `now-or-refuse` job in a commit is refused and removed instead) and, either way, ends that admission round. At its start the runner settles every attempt whose container is gone and that has no end recorded (D10), so a crash's attempt ends `error` unless a marker or `result.json` says otherwise, one without its started marker is undone (queued again) unless it holds a cancel marker or the never-started limit ends the run `error`, and a restart marker queues the next attempt; it waits on every job container still running, deletes the scratch of ended attempts, never a live container's (job containers outlive a runner restart, and a verb may start one first), and admits the queue, held restarts first.

### D10. One container per attempt
Runs are named so the two machines never collide: the laptop numbers its own runs `l1`, `l2`… and the VM its own `v1`, `v2`…, per id; the VM returns its run name in every commit answer, preflight state and `status` reply, and keeps its state (queue entry, markers, outcome) per run, so a stop hook writes only its own run's outcome. A run moved from the laptop keeps its laptop name on the VM. A run may take several attempts: a lane restart (D9) starts a new one, continuing the same run; a laptop run is attempt 0, and VM attempts count from 1 (a moved run's too) and a number is never reused, an undone or failed-start attempt's included, so no new container meets a leftover one of the same name. Each attempt has its own container and directory: `podman run -d --name tlcq-<id>-<run>-<attempt> --cpus … --memory … --label tlcq.attempt=… -v tlcq-state:/state <image> tlcq exec <id> <run> <attempt>`, `--memory` covering heap, off-heap and JVM overhead, its directory and TLC's scratch on the state volume rather than in the container's own layer. Because no two attempts share a container name, a new attempt or a new run never waits for an old container to go, and its stop hook can start the next one at once. The runner removes a container once it has settled it. A restart's next attempt is queued only by the previous attempt's stop hook (or a later settling, if the hook was killed or never ran) applying its restart marker, and a restart attempt that is undone or whose container fails to start returns to its queued restart, still holding the 70% slot, so a run has one live attempt at a time; once queued, any admission may start it (the hook's own, `commit`, a poll, the runner's start), so a low disk or a failed container start only delays it. The attempt's directory holds its markers, `result.json`, scratch and progress-curve segment, so every attempt starts clean.

The supervisor enforces the time cap itself, since it also makes the lane decisions that change it: it counts the cap from the attempt's start (a restart at 70% as max gets the full 12 hours), and at the cap writes a timed-out marker and stops TLC. `--timeout` counts instead over the run's VM attempts' running times added up. A run's duration is its attempts' running times added up (a moved run's laptop attempt in awake time, which the move's `job.json` carries), never its time in a queue; each new attempt's first `result.json`, written by admission (below), carries the run's lane decisions, duration so far and VM running time so far, and the last recorded attempt's file is the run's result. The supervisor writes `result.json` atomically.

`cancel` of a queued job (a run with no recorded attempt; a restart's queued next attempt follows the restart rule below) ends it `cancelled` at once, its outcome, label and any "replaced by" id kept with its queue entry and reported from there (it never started, so `fetch` returns no `result.json` for it); of a running one, it writes a cancel marker carrying the canceller's label and any "replaced by" id, asks podman to stop the container without waiting for it (D6), and returns: the job ends `cancelled` when its container has exited.

**Settling an attempt.** When an attempt's container has exited, the runner, which waits on every attempt's container, settles it under the admission lock: this is the stop hook. The outcome comes from the attempt's directory, first match wins: the cancel marker (`cancelled`, with its label and id); an outcome in `result.json`, which the supervisor writes only when TLC exits on its own, never after stopping it (so a verdict reached just before a restart or a cap is kept); the restart marker (no outcome, the end "restarted"); the timed-out marker (`timeout`); the too-big marker (`error`, too big); else `error` (a shutdown or an out-of-memory kill). The hook then writes the cache, then for a restart the next attempt's queue entry (keyed by its attempt number, so writing it twice is harmless), and last the attempt's end in `result.json`, the commit point; then it deletes the scratch and runs admission. Slot use is derived, never stored: a slot is busy while it holds a recorded attempt with no end, or a restart marker in such an attempt or a queued restart not yet recorded or dropped holds it, so recording the end frees the attempt's slots, and the held 70% slot too unless a restart was queued. The supervisor's first act is a "started" marker; a gone attempt without it never ran, and settling undoes it like a failed container start (record and directory deleted, the job queued again) instead of ending it, unless it holds a cancel marker, which ends the run `cancelled` (else a cancel landing before the supervisor starts would be lost). A run undone 3 times in a row (configurable; only a container gone before its started marker counts, and a started marker resets the count, and a failed container start neither counts nor resets it) ends `error` ("never started") instead, so a supervisor that cannot start does not loop: a run-level outcome written, like a cancel's, into the last recorded attempt's `result.json` (whose end stays as it was), or kept with the queue entry when the run has no recorded attempt; its queued restart and held slot (if any) are dropped with it. Admission records an attempt in its run's state, creates its directory and writes its first `result.json` (the run's lane decisions, duration so far and VM running time so far, copied from the previous VM attempt, or for a moved run's first VM attempt from `job.json`) before starting its container, and deletes them if the start fails: the job stays queued, or a `now-or-refuse` job in a commit is refused and removed. Every verb takes the admission lock, `preflight` included (it writes only token tombstones), so none sees a state between another verb's settling and its apply; each verb that writes first settles, the same way, each recorded attempt whose container is gone and that has no end, and deletes the scratch of ended attempts, before it applies anything; read-only verbs (`preflight`, `ls`, `fetch`) report such an attempt as settling would. So a hook that was killed (or missed while the runner itself was down) or never ran (a crash) is made good by the next writing verb (`commit`, `status`, `cancel`) or the runner's start, and settling twice changes nothing.

A cancel or supersede of a run with a restart pending: while the previous attempt's container still stops, the cancel marker goes in that attempt's directory, outranks the restart marker, and the run ends `cancelled` at its stop, freeing the held slot; once the hook has queued the next attempt, the cancel drops it and its held slot and ends the run `cancelled` at once, writing the outcome, its label and any "replaced by" id into the last recorded attempt's `result.json` (an attempt's directory and `result.json` are created when admission records it, so a dropped queued attempt leaves none). Until admission records its next attempt, a run with a restart pending counts as running: for the older-version rule, the preflight's per-id state and `status`. The queue is stored on disk.

**Checkpoints.** A run may hold a TLC checkpoint in `<state>/checkpoints/<id>/<run>/`: TLC's checkpoint directory `tlc/` and a `checkpoint.json` with the workers it ran with and its fingerprint function (`-fp`, from the start of its log). The run's next attempt recovers it (`-recover`) with those workers, since TLC keeps one file per worker, and that fingerprint function, since the recovered fingerprints were taken with it; TLC then goes on checkpointing into the same directory, and deletes it when it finishes. TLC's count of generated states starts again from the states it recovers, so `checkpoint.json` also keeps the run's generated states at the checkpoint, and the recovered attempt's curve, counters and result carry the run's count on from there (the estimators of D15 read generated states). A resize (D9) moves the checkpoint TLC has just written out of the attempt's scratch into the run's checkpoint directory, unless the attempt recovered one, which TLC checkpoints into in place; a lane restart, which stops TLC at once, past its last checkpoint, deletes the run's checkpoint, so the restart starts afresh. Settling deletes the checkpoint of every ended run, as it does the scratch of every ended attempt, so checkpoints never pile up. A checkpoint is data for the supervisor, not a state of the run: the runner model has the resize as a restart (`SupResize`) and leaves the checkpoint out. A container the runner lists as live includes a paused one, which is frozen, not gone; else settling would end it `error` and remove it.

### D11. Progress
`ls` and `status` report the fields the job-status spec lists; the growth numbers are `tla/probe.sh`'s (queue / distinct, and queue growth over 5 minutes / distinct). Each `status` is one short VM call, made whenever the agent polls, so a sleeping laptop or lost network only delays its answer. A report follows the run its agent placed or attached to (`l<n>` or `v<n>`, D10: the run its follow names, D6), so a run placed anew under the same id, by another worktree, is not mistaken for its own.

### D12. Seams for tests
The coverage floor needs every path reachable without pve, Docker or podman. The remote command is configurable (default `docker --context pve exec -i tlcq-runner tlcq`), so tests run the VM verbs against a temporary state directory locally. The container launcher is an interface: podman through its socket in the runner, a child process in tests. Caps, the poll interval and the clock (with separate awake and wall readings) are configurable, so a test can time out, or sleep, in a second.

### D13. Configuration and state
Each machine reads `~/.config/tlcq/config.toml`: the docker context (default `pve`), the runner's container name and the job image, the connect timeout (default 10 s: a call that only reads, the preflight, `status`, `ls` and `fetch`, with no byte of its reply by then finds the VM unreachable; a `commit` or `cancel` cut short may have been applied, so it waits out the deadline instead) and per-call deadline (default 2 minutes; the VM keeps it too, for reading and validating a payload), the free-disk floor (default 20 GB on the VM, 10 GB on the laptop, as `tla/tlc.sh`), the tarball limits (default 16 MB uncompressed, 2000 entries), the laptop's slot, workers and heap, the reserve, max share and heap fraction, the caps, the lane timers, probe times and thresholds (15 minutes; 0.4, 0.1 over a 5-minute window), the never-started limit and the poll interval (how often a waiting laptop supervisor rechecks the slot and disk, default 5 s), each defaulting as given here. State lives under `$XDG_STATE_HOME/tlcq` (`~/.local/state/tlcq` when unset, as on macOS): job directories, the follows, the placement lock, the cache (`results/<id>.json`), the history, an append-only JSONL file written under a lock, and each attempt's progress curve (`curves/<id>-<run>-<attempt>.jsonl`, D15). The label is the git top-level directory's name, the worktree's path and branch, and `$TLCQ_AGENT` if set.

### D14. The protocol is model-checked
Prose review of D6 and D7 kept finding races, so the protocol is a TLA+ model, `tla/placement/Placement.tla`, checked with TLC. It has commands from two worktrees placing jobs under the placement lock, with entries on the laptop and the VM, the laptop's mirror and pending offline entries; laptop supervisors (lock handoff, the slot, timeouts, moves, crashes); `cancel`; commits whose reply is lost before or after they apply; commands killed at any step; and the VM becoming unreachable. Its invariants: a job is never on the laptop and the VM at once (`NoTwoPlaces`); a laptop record with a free job lock has no live supervisor (`OrphanSound`); no worktree has two versions running (`OneVersion`); one worktree's supersede never cancels a job another worktree still follows (`WaitersRespected`); and no deadlock. `PL.cfg` (two commands, a cancel) and `PL3.cfg` (three commands) pass. Each `PL_<bug>.cfg` re-introduces one race the reviews or TLC found, with its `must fail` header: the lock handoff gap, attach by laptop record only, unresolved records treated as gone offline, no write-ahead `sent?`, laptop supersedes after the commit, a write-ahead record without its own entry, pending entries missing from the older-version scan, a supersede that ignores other worktrees' entries, pending entries flushed after supersedes, an attach exempt from the older-version rule, a supersede that keeps the worktree's pending entries, and a `sent?` record refreshed by its token instead of the id. A report follows its run (each placement anew counts a new run), a pending entry names its run (for a `sent?` record, the run its commit reached, as its token resolves) and is flushed only onto it, and an attach that lands, offline, on a run already superseded reads the cancel once the VM is back. Every config declares `SYMMETRY Symm` (commands, worktrees and ids are interchangeable), which shrinks the search 8–24× without changing a verdict (`PL3`: 15.8M states in 2 minutes, against 378M in 2 hours). Left out of the model: the generation counter (polls apply atomically); the agents of a commit whose reply is lost, which the model ends at once (the design has their follows wait for a refresh to resolve the token); tombstones (commits apply atomically in the model, so no lookup races one); verbs that reach the runner before its start-up settling; an `invalid` answer (nothing applied, and the command undoes its `sent?` writes and their follows, so its records are as before the commit, less the superseded laptop runs and the worktree's pending entries dropped from superseded jobs); a commit answered `cached` (the run ended cached since the preflight: the record ends, as the next poll would end it); a `now-or-refuse` job the VM refuses, whose `sent?` record becomes a laptop record (safe: the VM never stored the job); slot shares, caps and lane decisions, restarts included (a restart continues the run, like a move); cache contents beyond cached or not; batches (one job per command, so no all-or-nothing refusal of a batch and no slot handout); more than one configuration (an entry is just its worktree); and the expectation and route, which the model chooses freely among the allowed ones. A change to D6 or D7 changes the model first.

The VM runner of D9 and D10 has its own model, `tla/runner/Runner.tla`, after prose review of restarts and stop hooks kept finding races too; pinned-slots (S7) reshaped it for its two pinned slots, freeze and pause. It has runs and their attempts and containers, derived slot use over the E and P slots (P closable from the page), the supervisor's markers, TLC ending on its own, the stop hook settling step by step with a kill between any two steps, settling by writing verbs, read-only verbs under the admission lock, cancel and supersede, a failed container start, crashes and the runner's start, and the page's actions (bounded by `MaxUi`): freeze, thaw on spare capacity and refreeze, unfreeze, the pause request with the supervisor's paused stop marker and the checkpoint kept after it, a frozen job's pause (unpaused, stopped at once, or `cancelled` with no checkpoint), resume and the P toggle. Its invariants: a run has one live attempt, frozen included (`OneLiveAttempt`); no slot holds two jobs, thawed ones included (`SlotsExclusive`); nothing starts or thaws in a closed P slot (`ClosedSlot`); a pausing job is never frozen (`PausingNotFrozen`); a paused attempt's checkpoint was kept (`PausedHasCheckpoint`); a paused run stays paused, crashes included, until a resume or cancel (`PausedStays`); a cancelled run never starts again and is not paused (`CancelFinal`); a run counted as running has a live attempt, a queued next attempt or an attempt still to settle (`NoStuckRun`); settling twice changes nothing (`SettleTwiceNoop`); an attempt ends `error` only when it ran and then crashed or died with no marker or outcome to say otherwise (`ErrorOnlyAfterCrash`); no new container meets a leftover one of its name (`NoNameClash`); no run is undone past the never-started limit (`UndoLimit`); a preflight's report of an ended run stands (`PreflightTrue`); and no deadlock. `RN.cfg` (two ids, a pause and its resume, two crashes, two cancels), `RN2.cfg` (one id run three times) and `RN3.cfg` (a pause, then an undone resume started again) pass; each `RN_<bug>.cfg` re-introduces one race the reviews or TLC found (`RN_noundoonfail` two, since the started marker alone covers a failed container start), among them the one TLC found in the design: a cancel landing before the started marker, lost when settling undid the attempt; and pinned-slots' own: the stop before the paused marker (`RN_stopbeforemark`), a paused stop ranked over a cancel (`RN_pausedovercancel`), a cancelled paused run settled paused again (`RN_resettleended`), a pause settled by its request (`RN_pausebyrequest`), a paused end without its checkpoint (`RN_nockcheck`), and a thawed job's slot counted free (`RN_thawedfree`). Units there are containers, the stop hook is the runner waiting on each one, and boot is the runner's start (a runner that dies while job containers run is a hook missed and made good later). Lanes, caps and times are left out (a cap or a checkpoint may fall due at any moment, frozen time is not modelled), admission picks freely among what the slot rules allow (so first in, first out, E first, and any order a human sets in the UI, are among its orders), and a run that has used its attempt numbers is outside the bound (the never-started limit, modelled with a lower count, ends a run within it). A change to D9 or D10 changes this model first.

### D15. ETA
`status` gives a running job an estimated end time, with its source. A study of a real project's TLC logs (`tmp/eta/REPORT.md`) found the basis: queue / distinct (Q/N) follows a nearly universal curve against the share of the work done (generated / final generated), and generated states grow about linearly in time at constant speed. So Q/N locates a run on its way, and the generated-states rate turns what remains into time. Raw counts at the same moment cannot do this: early on, a bigger model and a slower machine look alike.
- **With a previous run of the same configuration** (the latest full run, explored to the end, under D5's exact or configuration key, taking its last attempt's curve; with none, the first-run estimate): find the last point of that run where its Q/N was still at or above the current one; scale its remaining time by the size factor (distinct now / distinct then) and the speed factor (its generated rate there / the current 5-minute generated rate); and take the geometric mean with a fit of that run's Q/N shape to the current curve. Median error on real reruns: 2 % of the total at 15 minutes.
- **First run** (or only D5's name key): the geometric mean of two estimates: Q/N regressed on generated states over the last half of the run and extrapolated to 0; and the population's median Q/N shape (from other specs' runs) fitted with a free level. Each is divided by the current generated rate. Median error 9 % at 15 minutes, 98 % of estimates within 2×. With only the name key, the history and first-run estimates are averaged.
- A configuration with temporal properties gets about 22 % more for TLC's final temporal check, which prints no progress; once that check starts, its own tail replaces the estimate.
- No ETA before 5 minutes (3 progress lines) into the current attempt, whose own curve the estimators read. A run stopped by a violation ends before any estimate says, which `status` cannot foresee; future slowdowns cannot be foreseen either, so the ETA is recomputed at every poll from the current rate.

The estimators need each run's whole progress curve, not only its duration: the supervisor records one JSONL line per progress line (awake seconds since the attempt's start, at TLC's own spacing, depth, generated, distinct, queue; about 30 kB for 5 hours), the final counts, the start and length of the final temporal check, whether the configuration has temporal properties, the outcome, the workers and slot share, and the gaps where awake time and wall time diverged. The ETA is computed on the laptop, which holds the history and its keys: a VM job's curve travels in every `status` reply and with its result, and the laptop stores it with its own runs' curves, which also form the population for first-run estimates. The study's thresholds and windows were tuned on 57 runs from 9 model directories; the recorded curves let them be tuned again as tlcq's own history grows.

### D16. A web UI on the runner
The runner also serves a web page, behind the traefik already on pve and like the other services there (`Host(`tlcq.pve.local`)`, home network, no login), so a human can watch the queue and steer it:
- **Shown:** the two slots and what holds each (a job, a held restart, nothing); the queue in its order; each running job's progress (TLC's counters and rates, queue / distinct and its growth, the probe's numbers, its lane and the source of it, its cap and time left, its ETA); ended jobs, the latest end first and a page at a time, with outcome, exit status, duration and logs; and each job's submitters (worktree and label). A TLC log opens under its job's row, a running job's followed as it grows. The page refreshes itself from the runner's state every few seconds.
- **Built:** a React app in `ui/` (TanStack Query for the polling and the actions), built into the job image and served by the runner from `TLCQ_UI_DIR`; the runner's JSON API is `/api/state`, `/api/ended`, `/api/output` (a log), `/api/cancel`, `/api/reorder`, `/api/pause` and `/api/resume`.
- **Pause and resume:** the queue's header offers "Pause", which writes the stopping mark (D10), so admission starts nothing while running jobs go on; while the mark holds the queue it says so and offers "Resume", which clears the mark and runs an admission round, as the runner's next start would.
- **Cancel:** the same cancel as `tlcq cancel` (D10), its canceller labelled `ui`; agents read `cancelled`, by `ui`, at their next poll.
- **Reorder:** move a queued run up, down or to the head. It changes only the queue's order, never a run with a recorded attempt and never a held restart, which keeps the head; new runs still join at the tail.
- **ETA:** the runner computes it with D15's estimators (a module both sides share) from the curves of the runs it holds: a previous VM run under the exact or configuration key, else the first-run estimate. The laptop's `status` can differ, since its history also holds laptop runs.

Each UI action is a verb under the admission lock, like any other, so the UI adds no new state and no new race: cancel is in the runner model, and admission there already picks among every order the slot rules allow.

## Risks / Trade-offs

- [The first run of an unknown configuration costs up to 5 laptop minutes] → once per configuration: the timeout is recorded and later runs go to the VM.
- [A non-max job at 100% makes every later job wait until it ends] → bounded by its cap (or `--timeout`); short jobs meanwhile run on the laptop.
- [A job's speed depends on its slot: 100%, 70% or 30%] → the side slot's cap is longer, and durations are recorded as they are.
- [A useful run can be cut at its cap] → `--timeout` and `--max` raise it; the timeout is recorded, so the next run goes a lane up.
- [Commands queue for the placement lock] → a command holds it for one preflight and one commit call, each bounded by its deadline.
- [A `must fail` verdict can vary between runs and is then cached] → the mismatch suggests `--must-fail-only`.
- [The free-disk floor reserves nothing] → a job that fills the disk ends `error`, uncached.
- [The UI has no login] → it is on the home network only, behind traefik; anyone there can cancel or reorder jobs, and every cancel names `ui` as its canceller.
- [The runner is a service, and its podman socket gives it control of every container of the `podman` user on pve] → it only creates, waits on, stops and removes containers named `tlcq-…`; its restart policy restarts it if it dies, and job containers keep running meanwhile (D9).

## Migration Plan

Build the job image (Java, the pinned jars, the `tlcq` binary for Linux) from a Dockerfile in this repository, run the runner on pve as a compose service (`docker/compose.pve.yaml` over `docker/compose.yaml`: the image built on pve, the state volume, the podman socket, `restart: always`, traefik labels for the UI, D16), put the same jars on the laptop, add `tlcq.toml` to each model directory of the first project to use it, and route that project's runs through tlcq; `tla/tlc.sh` stays for offline runs. As with `tla/tlc.sh`, `tlcq submit <dir>` skips the max configurations unless `--all` is given.
